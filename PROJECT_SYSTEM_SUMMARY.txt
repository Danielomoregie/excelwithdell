Project Technical Summary for AI Engineer Handoff
Generated from current repository state.

1. Project Overview
This project is an AI-assisted product risk intelligence system for FusionTech laptop reviews.

High-level purpose:
- Ingest and analyze customer reviews.
- Convert review sentiment and complaint patterns into product-level risk scores.
- Estimate revenue exposure for risky products.
- Surface results in a web dashboard for internal teams (Engineering/IT, Marketing, Sales).

Business problem solved:
- Teams need early detection of product quality and sentiment issues before they become large business losses.
- The system aggregates unstructured review text into actionable signals: alerts, complaint themes, trend charts, product-level risk, and estimated monthly revenue at risk.

Dashboard purpose:
- Provide executives and department users an at-a-glance risk summary.
- Allow drill-down into product-level details, risk drivers, and recent negative feedback.
- Support lightweight AI Q&A via a template chatbot endpoint.

4. Machine Learning Model
Where the .pkl is located:
- `src/models/Risk_Model_Artifacts.pkl`

Model type:
- This is not a single supervised classifier/regressor model.
- It is a composite artifact bundle built from:
  - Rule-based sentiment classification (VADER thresholds).
  - Rule-based complaint theme extraction.
  - Weighted risk scoring formula (0-100).
  - Optional TF-IDF vectorizer fitted on negative review text.
- Operationally this is a risk scoring and analytics pipeline, not a standard trainable predictor class.

Library used to create it:
- pickle for serialization.
- nltk VADER for sentiment scores.
- scikit-learn for TF-IDF vectorizer.
- pandas/numpy for transformations and scoring computations.

Training data used:
- Database table `cleaned_train_80_percent`.
- Pulled in `src/Train_Model.py` from Neon PostgreSQL.

Expected inputs (pipeline level):
- Review-level fields including (at minimum):
  - `text`, `title_x`, `rating`, `asin`
- Additional fields used in scoring/trends:
  - `date`, `average_rating`, `helpful_vote`, `price`, `title_y`

Outputs produced:
- Artifact dictionary with keys:
  - `enriched_df`
  - `tfidf_vectorizer`
  - `risk_results`
  - `risk_trends`
  - `global_themes`
  - `alerts`
  - `portfolio_impact`

How dashboard loads and uses the model:
- `Flask_API.py` loads `Risk_Model_Artifacts.pkl` at startup into global `artifacts`.
- Dashboard APIs read from `artifacts` in-memory to render KPIs, tables, charts, detail views, and chatbot responses.

Exact code that loads the model (from `src/Flask_API.py`):

ARTIFACTS_PATH = os.path.join(os.path.dirname(__file__), "models", "Risk_Model_Artifacts.pkl")

artifacts = None


def load_artifacts():
    global artifacts
    if not os.path.exists(ARTIFACTS_PATH):
        raise FileNotFoundError(
            f"Model artifacts not found at {ARTIFACTS_PATH}. Run Train_Model.py first."
        )
    with open(ARTIFACTS_PATH, "rb") as f:
        artifacts = pickle.load(f)
    print(f"Loaded model artifacts ({len(artifacts['risk_results'])} products)")


5. Data Pipeline
Data source:
- Source CSV in repo: `Dataset_Scripts/CSV_Files/FusionTech Online Reviews_Initial.csv`.
- Uploaded to Neon table `online_reviews` using `Upload_Online_Reviews.py`.

Cleaning/prep flow:
- `Dataset_Resizing.py`: keeps data in target date window.
- `Duplicates_Check.py`: removes near-duplicate rows by text/rating/id proximity.
- `Deleting_Empty_Columns.py`: drops fully empty columns.
- `Temporal_Split.py`: sorts by timestamp/date and creates chronological train/test CSVs.
- Final training/test data expected in Neon tables:
  - `cleaned_train_80_percent`
  - `cleaned_test_20_percent`

How predictions/risk are generated:
- `Train_Model.py` pipeline:
  1) Pulls train table from Neon.
  2) Runs sentiment analysis.
  3) Trains TF-IDF vectorizer on negative reviews.
  4) Computes product risk scores and alerts.
  5) Computes revenue impact estimates.
  6) Computes trend series and serializes artifacts to `.pkl`.

How outputs are stored/displayed:
- Stored in artifact file `src/models/Risk_Model_Artifacts.pkl` (not per-product score persistence in DB by default).
- Displayed through Flask API endpoints consumed by `src/static/dashboard.js`.
- Customer-submitted reviews are persisted to DB table `fusiontech_submitted_reviews`.

9. Current Limitations

- Department-specific data filtering is scaffolded but not implemented.

10. How a Chatbot Could Integrate
Where chatbot can access predictions and insights:

Option A: API-first integration (recommended)
- Use existing endpoints:
  - `/api/dashboard` for KPI and alert summaries.
  - `/api/products` and `/api/products/<asin>` for product risk and detail.
  - `/api/trends` for time trends and theme stats.
  - `/api/profile` for user and department context.
- Add a new endpoint like `/api/chatbot/query` that:
  - Receives user question + optional department context.
  - Retrieves relevant API data.
  - Formats context for LLM call.
  - Returns grounded response with cited metrics.

Option B: Direct in-process access
- Chatbot service inside Flask can read global `artifacts` directly.
- Pros: lower latency.
- Cons: tighter coupling, harder to scale independently.

Department-aware chatbot behavior:
- Use current user department from session/profile.
- Apply role templates, e.g.:
  - Engineering: top defect themes, low-rating spikes, technical issue clusters.
  - Marketing: sentiment trajectory, brand tone shifts, campaign-sensitive signals.
  - Sales: product recommendations, revenue risk by product, customer objection themes.

Data grounding strategy:
- Always ground answers in data from `artifacts` or DB tables.
- Return metric values and period windows to avoid hallucinated recommendations.
- Consider adding source metadata in responses (endpoint + timestamp + record counts).

Suggested integration point in current architecture:
- Extend existing `/api/chatbot` route from template matching to retrieval-plus-generation pipeline.
- Keep fallback template mode when LLM unavailable.
